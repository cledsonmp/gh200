O Problema: O Runner Não Roda npm install para Você

Quando você desenvolve uma Action em JavaScript, é comum utilizar bibliotecas auxiliares oficiais, como o @actions/core e @actions/github, para manipular entradas, saídas e logs.

No entanto, quando um repositório consumidor utiliza a sua action através de uma referência externa (ex: uses: seu-usuario/sua-action@v1), o GitHub Actions não executa um npm install dentro da pasta da sua action. O runner apenas localiza o arquivo de entrada (entrypoint) declarado na propriedade main do seu arquivo de configuração (action.yml) — por exemplo, apontando para dist/index.js — e tenta executá-lo imediatamente.

Se as dependências do projeto não estiverem fisicamente presentes e disponíveis junto a esse arquivo, o Node.js falhará na hora com o erro clássico:

Cannot find module @actions/core.

A Solução: O Empacotamento em Bundle

Para que a action funcione perfeitamente sem exigir que o consumidor configure ou instale nada, o autor da action deve adotar a prática indicada na alternativa A:

  1. Gerar um Bundle Autossuficiente: Durante o processo de desenvolvimento (ou build) da action, utiliza-se uma ferramenta de empacotamento (como o @vercel/ncc, esbuild ou webpack). Essa ferramenta pega o seu código-fonte e todas as dependências do node_modules e as compacta em um único arquivo consolidado (o bundle).

  2. Versionar os Artefatos Compilados: É responsabilidade do autor garantir que esse arquivo final gerado (geralmente salvo em dist/index.js) seja devidamente commitado e publicado no repositório da action. Dessa forma, quando o runner baixar a action para executá-la, todo o código e suas dependências já estarão empacotados e prontos para rodar.

Onde entram o @vercel/ncc, o esbuild ou o webpack?

Lembra que o GitHub Actions não roda npm install quando baixa a sua action na máquina do usuário? Ele apenas lê o seu arquivo action.yml e executa diretamente o arquivo principal apontado pela propriedade main (por exemplo, main: dist/index.js).

Como o seu código-fonte usa dependências externas (como require('@actions/core')), se você subir apenas os arquivos soltos, o Node.js vai quebrar dizendo que o módulo não existe. É aqui que entram essas ferramentas de bundling (empacotamento).

Você roda o empacotador antes de publicar: Em vez de subir a pasta node_modules inteira para o repositório (o que é pesado e má prática), você usa o @vercel/ncc para compilar tudo em um único arquivo autossuficiente:

Bash

npx ncc build src/index.js -o dist

  • O que o @vercel/ncc (ou esbuild/webpack) faz por baixo do pano? Ele lê o seu código, busca o código do @actions/core dentro da pasta node_modules, e injeta tudo dentro de um único arquivo final chamado dist/index.js.

  • O resultado que você comita no repositório da Action: O arquivo dist/index.js gerado fica gigante e feio, mas dentro dele já estão o seu código e todas as dependências embutidas.

Quando o usuário do seu workflow chama a sua action (uses: seu-usuario/sua-action@v1), o GitHub baixa esse arquivo pronto em dist/index.js, o Node.js o executa imediatamente, e ele roda sem precisar de nenhum npm install!

Package.json

Como o empacotador (como o @vercel/ncc) vai ler o seu código-fonte, juntar tudo o que você precisa e transformar em um único arquivo final (dist/index.js), o seu package.json acaba tendo uma divisão muito importante: as dependências de produção vão para as devDependencies (porque o código final já vai embutido no bundle) e você usa um script de build para gerar o arquivo.

O que cada parte significa aqui?

  1. "main": "dist/index.js": É o ponteiro que o GitHub Actions lê no seu action.yml (através de main: dist/index.js). Ele diz ao runner exatamente onde está o arquivo pronto para ser executado.

  2. "devDependencies": O @vercel/ncc e bibliotecas como @actions/core ficam aqui. Durante o desenvolvimento, você precisa delas instaladas localmente para programar e compilar. Mas quando o ncc build roda, ele pega o conteúdo dessas bibliotecas, "succiona" para dentro do arquivo de saída (dist/index.js) e deixa tudo pronto.

  3. "scripts": { "build": ... }: É o comando que você roda no seu terminal (ou automatiza em um workflow de CI/CD próprio da sua action) antes de enviar uma nova versão para o GitHub. Quando você roda npm run build, ele gera o arquivo empacotado na pasta dist/.

É por isso que, quando você for commitar os arquivos para o repositório da sua action, você envia a pasta src/, o package.json, mas também garante que a pasta dist/ gerada pelo build esteja commitada, pois é ela que o GitHub vai baixar e executar direto!
