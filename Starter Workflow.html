Starter Workflow



O conceito de Starter Workflows existe e é oficial no ecossistema do GitHub! Inclusive, você provavelmente já usou sem perceber quando clica na aba "Actions" de um repositório novo e o GitHub sugere modelos prontos para Node.js, Python, Docker, etc.

Vamos entender o que ele é, por que é a resposta certa para essa questão e como se difere de outros recursos.

O que é um Starter Workflow?

Um Starter Workflow (ou modelo de inicialização) funciona como um esqueleto ou template de ponto de partida.

Quando uma equipe ou organização quer padronizar os primeiros passos dos novos projetos, ela pode criar modelos próprios de arquivos .yml (geralmente salvos em um repositório especial na organização chamado .github). Quando um desenvolvedor cria um novo repositório ou vai adicionar uma action, ele pode escolher esse modelo.

Analisando a Questão

O enunciado dizia:

"Uma equipe quer oferecer um ponto de partida para novos projetos, permitindo que cada repositório adapte comandos e gatilhos livremente."

A resposta correta é a C: Starter workflow que gera uma cópia inicial editável.

Por que essa é a única que atende perfeitamente?

  1. Gera uma cópia inicial editável: Quando você usa um starter workflow, o GitHub copia aquele arquivo .yml para dentro do seu repositório.

  2. Liberdade total de adaptação: Como o arquivo agora mora dentro do seu repositório, você é o dono dele. Você pode abrir o código, mudar comandos, alterar gatilhos (on: push, on: pull_request) e customizar da forma que quiser.

  3. Sem sincronização forçada: Como explica a correção da imagem, alterações futuras feitas no template original da organização não afetam automaticamente os arquivos que já foram copiados para os repositórios dos projetos. Cada um ganha independência para evoluir o seu próprio workflow.

Por que as outras alternativas estão erradas?

  • A) Reusable workflow obrigatório, sem configuração no consumidor: Um reusable workflow (workflow reutilizável) fica centralizado em um lugar e os outros repositórios apenas o "chamam" como uma função externa. Se a regra exige que o repositório consumidor adapte comandos livremente ou edite o esqueleto, o workflow reutilizável engessa isso, pois ele roda o código centralizado sem permitir cópias editáveis locais daquela forma.

  • B) Composite action que define os eventos do repositório: Uma composite action serve para agrupar passos (steps) repetitivos de código dentro de uma action personalizada, mas ela não define os gatilhos globais (on: ...) de eventos do repositório nem serve de template inicial de workflow.

  • D) Artefato compartilhado que substitui o arquivo YAML: Artefatos são arquivos gerados durante a execução de um build (como .zip ou binários), e não arquivos de configuração de infraestrutura ou templates para iniciar um projeto.

Ficou claro o conceito do starter workflow como aquele modelo inicial que você copia para o repositório e ganha total liberdade para editar?
