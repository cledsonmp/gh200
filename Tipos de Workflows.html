Resumo prático para a prova:

  • Quer chamar um workflow dentro de outro workflow como se fosse uma função? ➔ workflow_call

  • Quer que um workflow rode automaticamente assim que outro workflow terminar? ➔ workflow_run

  • Quer um botão para rodar manualmente na interface do GitHub? ➔ workflow_dispatch

  • Quer receber um aviso/gatilho vindo de um sistema externo via API? ➔ repository_dispatch


workflow_run: Ele reage à conclusão (ao término) de outro workflow. Ele não é chamado diretamente para executar junto; ele serve para escutar: "O workflow X terminou de rodar? Então agora o workflow Y pode começar". Geralmente é usado para rodar relatórios de pós-build ou testes de segurança baseados no resultado de um build que acabou.




Vamos usar uma analogia do mundo real para o workflow_run que vai fazer todo sentido.

Pense no workflow_run como um fofoqueiro de plantão ou um fiscal que fica escondido esperando o trabalho dos outros terminar para poder agir.

Ele não roda junto com o outro workflow e não é chamado diretamente como uma função. Ele diz assim:

"Eu não quero saber o que está acontecendo agora. Só me avise quando o workflow X terminar de rodar. Assim que ele acabar (seja com sucesso ou erro), eu começo a fazer o meu trabalho."

Exemplo Prático: Relatório de Testes e Segurança

Imagine que você tem dois processos separados no seu projeto:

  1. O Workflow 1 (ci.yml): Roda toda vez que alguém dá um push. Ele compila o código e roda os testes unitários. Demora 10 minutos.

  2. O Workflow 2 (seguranca.yml): É um scanner pesado que procura vulnerabilidades no código. Como ele é muito pesado, você não quer que ele rode junto com o CI para não deixar o desenvolvedor esperando.

É aqui que entra o workflow_run! Você configura o seguranca.yml para rodar somente após o ci.yml terminar com sucesso.

Veja como fica o código do Workflow 2 (seguranca.yml):

name: Scanner de Segurança Pós-Build



on:

workflow_run:

workflows: ["CI Principal"] # Nome exato do Workflow 1 que ele vai fiscalizar

types:

- completed # Dispara assim que o Workflow 1 for concluído (terminar)



jobs:

analisar-vulnerabilidades:

runs-on: ubuntu-latest

steps:

- name: Rodando scanner de segurança

run: echo "O CI Principal acabou! Agora vou fazer a varredura de segurança."





A Grande Vantagem do workflow_run (O Superpoder dele)

Por que alguém usaria o workflow_run em vez de colocar tudo no mesmo arquivo?

Por causa da Segurança (Permissões). No GitHub Actions, se o seu repositório é público, workflows disparados por pull_request de pessoas de fora (contribuidores externos) rodam com permissões restritas para evitar que alguém mal intencionado roube seus tokens e senhas de acesso à produção por exemplo.

Porém, o workflow_run roda na branch padrão/principal e tem acesso a tokens e segredos sensíveis (secrets) com segurança, porque ele está apenas fiscalizando algo que já rodou e foi aprovado na base oficial.

Resumo para fixar:

  • workflow_call: É uma subrotina / função. Um workflow chama o outro e espera o resultado ali na mesma hora.

  • workflow_run: É um observador / pós-processo. Ele fica assistindo de camarote. Quando o workflow monitorado termina (completed), ele acorda e começa a rodar sozinho.
