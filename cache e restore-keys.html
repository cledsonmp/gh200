Esse conceito de Cache e restore-keys no GitHub Actions costuma confundir bastante, mas depois que você entende a lógica de "plano A, plano B e plano C", fica muito simples.

O Problema do Cache no CI/CD

Quando o seu workflow roda, baixar dependências (como os pacotes do Node.js na pasta node_modules) toda vez do zero deixa o build super lento. Para resolver isso, usamos a action de cache (actions/cache).

O cache funciona procurando um arquivo salvo anteriormente usando uma chave (key).

Analisando um exemplo de código.

temos:

key: npm-linux-hash-novo 

restore-keys: | 

npm-linux- 

npm-



Imagine que essa chave exata (npm-linux-hash-novo) foi gerada hoje porque você alterou um arquivo do projeto (ex: o package-lock.json).



O GitHub Actions faz o seguinte passo a passo:

  1. Tentativa 1 (A Chave Principal - key): O GitHub procura no banco de dados de caches se existe exatamente o cache chamado npm-linux-hash-novo.

    • Resultado no exemplo: Não encontrou (porque o hash mudou).

  2. Tentativa 2 (O Plano B - Primeira restore-keys): Como a chave principal falhou, o GitHub olha para a primeira linha de restore-keys, que é npm-linux-. Ele vai procurar no histórico se existe qualquer cache antigo que comece com o prefixo npm-linux- (por exemplo, um cache salvo semana passada chamado npm-linux-hash-antigo).

    • Resultado: Se encontrar, ele baixa esse cache antigo para que você não precise baixar tudo da internet! Ele aproveita a base do cache por correspondência de prefixo.

  3. Tentativa 3 (O Plano C - Segunda restore-keys): Se nem o prefixo npm-linux- for encontrado, ele tenta a próxima linha: npm-. Ele busca qualquer cache que comece com npm-.



O restore-keys não cria cópias e nem duplica nada. Ele serve apenas como um "plano de contingência" em cascata (fallback) para tentar achar um cache reaproveitável caso o cache exato e perfeito daquele commit ainda não exista.
